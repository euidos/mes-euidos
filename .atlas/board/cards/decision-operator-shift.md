### 작업자 식별

| 기준 | **A. 개인 로그인 계정** | B. 사원증 스캔 / PIN | C. 기록 안 함 |
|---|---|---|---|
| 실적에 남는 것 | 시스템 사용자 | 작업자 사번 | 없음 |
| 현장 단말 | 1인 1계정 | **공용 단말 가능** | 공용 |
| 교대 시 | 로그아웃·로그인 | 스캔만 | — |
| 계정 관리 | 인원수만큼 발급·회수 | 0 | 0 |
| 실제 귀결 | 공용 계정 1개를 돌려씀 → 식별력 0 | 유지 | — |

**채택: A (개정).** 작업자마다 개인 계정. 식별은 로그인 사용자에서 자동.
사원증 스캔/PIN은 폰이 없는 사람·대리 입력용 예비 경로로 유지.

```
작업자 개인폰
  설비 QR 스캔 → 로그인(최초 1회) → 실행 화면
  실적 입력 시 작업자 = 로그인 사용자
```

| 대상 | 방식 |
|---|---|
| 현장 작업자 | **개인 계정** + 개인폰 |
| 반장·기술·품질·관리 | 개인 계정 |
| 폰 없는 작업자 | 사원증 스캔/PIN 예비 경로 |

### 근무조

**자동 판정 + 근무 시작일 기준.** 작업자가 조를 고르는 입력 없음 —
`Shift Type` 의 시작·종료 시각과 실적 등록 시각으로 판정.

자정 넘김: 7/25 22:00 ~ 7/26 06:00 = 전부 **7/25 야간조**. 현장이 "어제 야간"이라 부르는 단위와 일치.

## Why

**개인폰 전제에서는 개인 계정이 실제로 작동함.** 본인 폰이라 로그인이 유지되고 교대 시 전환이
없으므로, 기각 사유였던 "결국 공용 계정 하나로 수렴한다"가 성립하지 않음.
출퇴근 기록·개인별 알림·교육 이력 같은 확장도 계정이 있어야 열림.

**두 질문을 분리해야 함**: "누가 데이터를 입력했나"(`User`, 보안·감사)와 "누가 작업했나"
(`Job Card.employee`, 품질·생산성). 반장이 대신 입력해도 작업자는 김OO인 경우가 실제로 많음 —
하나로 합치면 둘 다 부정확해짐.

## History

- 초안: **B. 사원증 스캔, 작업자 계정 없음** — 공용 단말 전제. `superseded`
  - 폐기 사유: 전제가 "호기 옆 공용 단말"에서 "작업자 개인폰 + QR"로 바뀜(`[[decision-shopfloor-execution]]`).
    공용 단말에서는 개인 계정이 공용 계정으로 수렴하지만, 개인폰에서는 그 실패 모드가 없음.

## Memory

Frappe 구조: `User`(로그인 주체)와 `Employee`(인사 레코드)는 별개 DocType.
`Employee.user_id` 로 연결할 수 있지만 **연결하지 않아도 Employee는 정상 동작** —
작업자 300명을 Employee로 등록하고 계정은 0개인 구성이 가능.

Job Card에 `employee` 필드가 이미 있어 스캔값을 넣기만 하면 됨. 개발은 입력란 하나.
사원증이 없는 업체는 4자리 PIN으로 같은 필드에 입력 — 스캔 장비 유무가 문진 항목이고
저장되는 값은 동일.

작업자 계정의 권한은 최소로 (마스터 수정·문서 승인 불가). 역할 설계는 로드맵 8번 권한·역할에서.
계정 종류 확정: **전원 System User** — 화면을 Desk 커스텀 페이지로 통일했기 때문
(`[[decision-ui-architecture]]`). 자체 호스팅이면 인원수 비용 0.

`Shift Type` 이 마스터에 남은 용도는 두 가지: 조별 불량률·생산성 비교, 비가동 집계의 기준 구간.
LOT 분기에서는 빠져 있음 (`lot_split_on_shift` OFF, `[[decision-lot-rule]]`).
자정 넘김 규칙이 LOT 코드에서 조를 뺀 이유 중 하나였고, 조별 집계에서는 근무 시작일 기준으로 해소.
