### 좌측 메뉴 — Frappe Workspace 6개

```
사이드바
  MES 현황      대시보드 · 리포트
  기준정보      품목 · BOM/라우팅 · 금형 · 설비 · 작업자 · 품질기준 · 문서 · 거래처
  생산          생산계획 · 작업지시 · 현장 실행
  품질          검사 · 불량/처분
  재고          재고 조회 · 입출고 · 실사 · 출하 · 외주
  설정          LOT 추적 · MES 설정
```

| 기준 | **A. 묶음별 6개** | B. 하나로 통합 | C. 역할별 |
|---|---|---|---|
| 화면 찾기 | 묶음 → 화면 | 22개 나열 | 역할에 맞는 것만 |
| 확장 | 묶음 유지 | 한 화면이 계속 비대 | 역할 늘면 증식 |
| 권한 | 역할 권한으로 | 동일 | Workspace가 필터 |

**채택 A.** 권한은 Workspace가 아니라 역할 권한으로 거는 것이 정석. 중소 공장은 한 사람이 여러 역할을
겸해서 C(역할별)가 오히려 헷갈림.

**현장 작업자는 예외** — 사이드바에 `현장 실행` 하나만 노출. 폰에서 메뉴를 헤맬 일이 없음.

| 대상 | 로그인 직후 첫 화면 |
|---|---|
| 관리·계획·품질 | 대시보드 |
| 현장 작업자 | 현장 실행 |

`User.default_workspace`(사용자별), `Role.home_page`(역할별)로 지정.

### 목록형 화면 표준 골격

```
┌──────────────────────────────────────────────┐
│ 품목                              [+ 등록]    │  제목 · 주 액션 1개
│ 원자재·반제품·완제품 등록                     │  한 줄 설명
├──────────────────────────────────────────────┤
│ [기간] [품목그룹] [검색어]          [초기화]  │  필터 바
├──────────────────────────────────────────────┤
│ 품목코드   품목명     그룹    재고   상태     │  표
└──────────────────────────────────────────────┘
```

주 액션은 우상단 **1개만** 버튼으로, 나머지는 `⋯` 안으로.

### 행 클릭 시 상세 — A 기본 + B 예외

| | **A. 우측 드로어(기본)** | **B. 별도 화면(예외)** |
|---|---|---|
| 목록 유지 | 유지 — 다음 행 연속 확인 | 사라짐 |
| 폰 | 전체화면 전환 | 그대로 |
| 적합 | 필드 위주 조회·수정 | 깊은 구조 / 이력·추세 |

**B 예외 기준 둘**
1. **내용이 깊고 넓음** — BOM·라우팅, 생산계획, LOT 추적
2. **이력·추세를 봐야 함** — 재고 품목(입출고 이력·변동 차트·LOT별 잔량), 금형(타수 추이·보전 이력),
   설비(가동/비가동 추이), 작업지시(진행 곡선·공정별 상태)

### 행 인라인 액션 — 읽기 계열만 허용

| 허용 | 금지 |
|---|---|
| 문서 열람, 라벨 인쇄, 복사, 다운로드 | **상태를 바꾸는 모든 동작** (합격 판정, 취소, 완료 처리) |

## Why

인라인 액션은 빈도가 높아도 **상태를 바꾸는 것은 위험이 이득을 넘음** — 검사 합격을 LOT 상세를 안 보고
누르게 되고, 확인 대화를 붙이면 클릭 수가 같아져 이득이 사라짐. 표에 동작 열이 생기면 데이터 열이
좁아지는 비용도 있음(폰에서 특히).

읽기 계열만 허용하면 규칙이 한 줄이라 **화면마다 다시 논의할 일이 없고** 되돌릴 것이 없어 위험이 0.

## Memory

좌측 메뉴는 우리가 만드는 컴포넌트가 아니라 **Frappe Workspace 구조**임
(`[[decision-ui-architecture]]` — Desk 셸 사용). Workspace 안에 바로가기·카드·차트를 배치하는 것도
Frappe 기본 기능이고 사용자가 개인화할 수 있음.

화면 목록은 `[[spec-screen-list]]` 22개. 뼈대를 전체 22개 기준으로 잡는 이유는, 나중에 화면이 늘 때
메뉴 재편이나 공통 부품 변경으로 이미 만든 화면을 다시 손대는 일을 막기 위함.
