**표준 리포트 세트를 제품에 내장. 고객 사용자는 리포트 빌더를 쓰지 않음** (`[[decision-ui-architecture]]` A-1).

| 완화책 | 목적 |
|---|---|
| **표준 리포트 세트 내장** | 생산실적·불량현황·금형현황·LOT추적·재고·OEE 등. 고객 요청 대부분을 흡수 |
| **모든 표에 공통 필터** | 기간·호기·금형·품목·품목그룹·LOT. "다른 표"가 아니라 "같은 표 다른 조건"이 되게 |
| **엑셀 내보내기 필수** | 나머지 변형은 고객이 엑셀에서 해결 |
| **도입 문진에 "필요한 표 목록"** | 계약 전에 요구를 드러냄 |

앞의 두 개가 핵심 — 표 개수를 늘리는 대신 **필터를 넉넉히** 두면 한 화면이 여러 요구를 커버함.

## Why

A-1의 유일한 실질 비용은 "이 표 좀 뽑아주세요"가 개발 대기열에 쌓이는 것. 표준 세트 + 넉넉한 필터 +
엑셀 내보내기로 대부분 덮이고, 남는 요청은 문진 단계에서 미리 드러남.

시스템 관리자(공급자 측)는 Desk 뒷문에서 리포트 빌더를 그대로 쓸 수 있음 — 능력을 잃는 것이 아니라
고객 사용자에게 노출하지 않는 것.

## Memory

**Frappe 리포트 종류 구분** (Frappe 16.28.0):
- **리포트 빌더** — 코딩 없이 목록 화면에서 열 추가·필터·그룹핑·소계·차트·저장·공유·엑셀 내보내기.
  한 DocType + 자식 테이블 + Link 한 단계까지. **무관한 두 DocType 조인 불가, 계산식 지표 불가.**
- **쿼리 리포트(SQL) / 스크립트 리포트(Python)** — 개발자가 작성. OEE처럼 여러 값을 곱해 만드는
  지표는 여기서 처리. 우리가 만들 표준 리포트가 이 자리.

즉 리포트 빌더는 단순 목록·필터 요구를 사용자에게 넘기는 장치이고, 실제 분석 화면은 어차피 제작 대상.
그래서 A-1로 막아도 잃는 기능 범위가 좁음.
