### 1차 묶음 (7개)
- [x] **품목** — 모든 것의 기준
- [x] **BOM** — 무엇을 어떻게 만드는지
- [x] **설비** — 어디서 만드는지
- [x] **작업지시** — 생산 지시
- [x] **실행 현황** — 실적 입력 경로 (PC 기준)
- [x] **재고 조회** — 결과 확인
- [x] **LOT 추적** — 제품의 존재 이유

### 1차에서 뺀 것과 임시 대응

| 뺀 화면 | 1차 운영 방법 |
|---|---|
| 금형 · 작업자 · 거래처 · 문서 · 품질기준 | Desk 뒷문에서 관리자가 등록 |
| 생산계획 | 작업지시를 수동 발행 |
| 검사 · 불량/처분 | 현장 실행에서 불량 수량만 받고 판정은 나중 |
| 입출고 · 실사 · 출하 · 외주 | Desk 뒷문 또는 수기 |
| 대시보드 · 리포트 | 없음 |
| 설정 | 기본값 고정 |

### 범위 밖 (현 단계)

| 항목 | 처리 |
|---|---|
| **모바일 화면 전체** | 나중에 Desk 밖 독립 주소로 별도 설계. 같은 사이트면 DB·DocType 공유라 연동 불필요 |
| 현장 실행의 QR·개인폰 진입 | 설계는 유효(`[[decision-shopfloor-execution]]`), 구현은 모바일 단계에서 |

## Why

**금형을 1차에서 뺀 이유**: 하네스 우선이면 압착 애플리케이터 관리가 초기부터 필요할 수 있으나,
Desk 뒷문 등록으로 버틸 수 있음. 1차의 목적은 기능 완비가 아니라 **한 줄기가 끝까지 흐르는 것**을
확인하는 것.

**현장 실행을 PC 기준으로 지금 만드는 이유**: 실적 입력 경로가 없으면 MES가 아니고 시범 운영 자체가
불가능함. 라인 옆 PC로 시작하고, 모바일이 나오면 병행하거나 대체 — 단일 화면이라 버려도 손실이 작음.

## Memory

업무 로직을 DocType 훅에 둔 결정(`[[decision-business-logic-placement]]`)이 여기서 값을 함 —
1차에서 뺀 영역을 Desk 뒷문으로 처리해도 LOT 분기·타수 가산·문서 스냅샷이 동일하게 동작함.
화면이 없다고 규칙이 빠지지 않음.

나중에 모바일 앱을 **같은 사이트에 추가 설치**하면 DB·DocType·훅을 그대로 공유함.
앱을 분리할 실익은 배포를 따로 가져갈 때(별도 버전·별도 판매·팀 분리)뿐이고, 아니면 같은 앱에
라우트만 추가해도 됨 — 그때 결정.

전체 화면 목록은 `[[spec-screen-list]]` 22개, 뼈대는 `[[decision-ui-shell]]`.
